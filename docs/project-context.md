## Product overview

Cursora (working title "CAPTCHA Service", still used for the Figma file and, misspelled, for the Jira project "CAPTHCA Service space") is a bot-protection service for third-party websites. An embedded JavaScript widget collects behavioural signals; a FastAPI backend with a rules-first Risk Engine, optionally helped by an ML score, decides `allow`, `challenge` or `block`; a challenged visitor gets an "I'm not a robot" checkbox and, if still suspicious, one interactive CAPTCHA; an Nginx gate in front of the site's protected routes forwards only requests from verified sessions. Site owners manage sites, sensitivity and statistics in an admin panel (`file:799857_captcha_service_presentation.txt#Короткий опис продукту`, `msg:799646`, `photo:808975`).

- **Problem:** "bots can imitate simple clicks, bypass frontend checks and attack the backend directly" (`file:799857_captcha_service_presentation.txt#Проблема та підхід`). Site owners need less spam, fewer brute-force attempts and automated requests on forms, registration, login and APIs, a backend that cannot be reached by bypassing frontend checks, and outcomes explained through statistics; legitimate users need a simple path (`photo:808975`).
- **Vision (Product Vision Board, 2026-09-29):** "Give websites manageable bot protection that combines traffic rules, behavioural signals, and CAPTCHA only when needed." Differentiator: "System-first: useful protection before the model is accurate." (`photo:808975`)
- **Origin:** on 2026-09-03 a team member (later an ML developer) proposed a CAPTCHA service that tells bots from humans by cursor movement using ML, or alternatively a whole request proxy "something like Cloudflare"; the team lead extended it to an interactive CAPTCHA plus traffic and request analysis, with the CAPTCHA required only on suspicion (`msg:794483`, `msg:794493`, `msg:794496`).
- **Motivating scenario (informal, 2026-09-08):** protect a content site's original articles from scraper ("plagiarist") bots (`msg:796951`, `msg:796952`); see OQ-3.

### MVP scope

- In the MVP (Decided): a JS widget that collects behavioural signals; a checkbox plus one interactive CAPTCHA type; a FastAPI backend with the Risk Engine and an ML baseline; Nginx in front of the demo site; PostgreSQL for sessions and results; an admin panel with sensitivity and statistics (`file:799857_captcha_service_presentation.txt#Функціональність MVP`, `file:799940_answer.md#answer 5`).
- Data for the model comes from the widget and a team-built bot behaviour generator (`file:798550_captcha_service_plan.md#Етапи`).
- Course-stage goal: "show the full path from the first request to the Risk Engine decision on a demonstration site" (`file:799857_captcha_service_presentation.txt#Функціональність MVP`).
- Business goals: deliver an integrated MVP that demonstrates site protection; validate the combination of rules, CAPTCHA and ML scoring; collect data for future model improvement; measure allow, challenge, block and false-positive rates (`photo:808975`).

## Business logic and domain rules

### End-to-end flow

Visitor (the 2026-09-14 user flow with the later clarifications applied, `msg:799646`):

1. The visitor opens a page of a site that embeds the widget (`<script src=".../widget.js" data-site-key="...">` in the repo).
2. The widget calls the session endpoint; the backend reuses the session from the cookie or creates a `new` one and sets the cookie (BR-1 to BR-3).
3. The widget passively collects behavioural signals; the backend gets request signals (IP, User-Agent, request rate) from the server or Nginx (BR-7).
4. Before a protected action the signals reach the backend, which applies the rules and the optional ML score and makes an initial decision: `allow` (no visible challenge), `challenge` (checkbox) or `block` (requests temporarily restricted) (BR-9, BR-10).
5. A checkbox click sends the accumulated data; on success the session becomes `verified`; if the visitor still looks suspicious, one interactive task is shown (BR-13 to BR-15).
6. The task is checked deterministically (correctness, time) and the behaviour is scored: `human` passes, `suspicious` gets another attempt, `bot` is temporarily blocked (BR-17 to BR-19).
7. On a protected route the browser sends the cookie to Nginx, Nginx asks the gate, and the session status decides: forward, challenge or block. Other routes are forwarded without a check (BR-20 to BR-22).
8. After expiry `verified` no longer counts; the next visit gets a fresh `new` session, and reputation is used only as a soft hint (BR-3, BR-4, BR-34).

Administrator and integration developer (`msg:799646`, `file:799857_captcha_service_presentation.txt#Підключення сайту адміністратором`):

1. Register (method Open, OQ-26), create a project and add members as ADMIN or DEVELOPER (BR-29).
2. Add a site: domain, allowed origins, origin backend address; receive the public site key (and a secret API key only if the token path stays, OQ-1) (BR-26).
3. Set sensitivity 0–100 (BR-27); other parameters are Open (OQ-25).
4. Point the domain or a test subdomain at the proxy (operator Open, OQ-2), close direct access to the origin, embed the widget (BR-23).
5. Check the integration in test mode (OQ-29) and view statistics (BR-30).

Decisions (`allow`/`challenge`/`block`) and verdicts (`human`/`suspicious`/`bot`) come from the user flow (`msg:799646`); the explicit mapping between them is the design pack's proposal DA-2 (`file:818551_DOMAIN_MODEL.md#2.5 State machines and business rules`), still Open (OQ-18).

### Sessions and signals

- **BR-1** The backend owns the verification session. On initialisation the widget calls the session endpoint and the browser sends the session cookie automatically; the backend reuses a valid session or creates a new one and sets the cookie. The widget never generates and preferably never reads `session_id` (`msg:799950`, `voice:799948`, `file:799940_answer.md#answer 1`).
- **BR-2** Session IDs are generated by the backend and kept unique by a database constraint; a new session always starts as `new` (`file:799940_answer.md#answer 1`, `file:799940_answer.md#answer 8`).
- **BR-3** A new session is created only if there is no cookie or the session is missing, expired or invalid; otherwise it is reused. A new session never inherits the old status (`msg:799958`, `msg:799960`).
- **BR-4** Sessions are short-lived (`expires_at` in PostgreSQL) and bound to exactly one site; after expiry `verified` no longer counts and the visitor is assessed again. Lifetime values are Open (OQ-7) (`file:799940_answer.md#answer 4`, `file:799940_answer.md#answer 7`, `msg:799646`).
- **BR-5** `session_id` only links the HTTP requests of one session: it is not a risk signal and not proof on its own. User-Agent and fingerprint are extra signals against reuse of the ID or its transfer to another client, such as an HTTP client with a hard-coded cookie (`msg:799951`, `file:799940_answer.md#answer 7`, `file:799932_user-flow-review.md#step 14`).
- **BR-6** Behavioural signals are stored in the database, linked to the session, as JSONB; a valid session is the primary key for joining events (`msg:799958`, `file:798550_captcha_service_plan.md#7. Data layer: PostgreSQL`, `photo:808975`).
- **BR-7** Signal set (Proposed; the final list and client-side vs hybrid collection are Open, OQ-15): from the widget, passively, cursor movements or touches, clicks and the pauses between them, time on page, browser and device parameters; from the server or Nginx, IP, User-Agent and request frequency (`msg:799646`, `msg:799959`).

### Risk evaluation and decisions

- **BR-8** System-first: protection must work without ML. Rules decide on their own; the ML score is an optional extra input that "provides additional criteria for our backend". A missing or untrained model must not stop decisions (mechanics Open, OQ-31) (`msg:798781`, `photo:798757`, `photo:808975`).
- **BR-9** The Risk Engine combines rule results and the optional ML result into an initial decision: `allow` (pass without a visible challenge), `challenge` (show the checkbox) or `block` (temporarily restrict requests) (`msg:799646`, `file:798550_captcha_service_plan.md#5. Risk Engine`).
- **BR-10** The initial assessment runs before any visible challenge; the checkbox appears only when the server decides a check is needed. When and on which data the initial assessment runs is Open (OQ-19) (`file:799940_answer.md#answer 3`, `msg:799946`).
- **BR-11** Rules are internal (request frequency, headers, IP, session state, etc.): site administrators neither see nor edit individual rules (`file:799940_answer.md#answer 2`, `photo:808996`).
- **BR-12** Candidate rule inputs (Proposed; rule set, weights and combination Open, OQ-16): request rate, IP, User-Agent, suspicious headers, session state, session reputation, token reuse, signs of automated traffic, a form filled in too fast (`file:798550_captcha_service_plan.md#5. Risk Engine`, `msg:799646`).

### Challenges (CAPTCHA)

- **BR-13** Verification is graduated: invisible assessment, then the checkbox (part of the widget), then, if the visitor still looks suspicious, one interactive task, then a final Risk Engine assessment (`file:799857_captcha_service_presentation.txt#Поступова перевірка`, `file:799940_answer.md#answer 3`).
- **BR-14** The checkbox click sends the accumulated behavioural data; on success the session becomes `verified` with the completion time recorded. What the click itself decides (a second "post-checkbox" assessment, DA-9) is Proposed (OQ-19) (`file:799940_answer.md#answer 3`, `msg:799646`, `file:818551_DOMAIN_MODEL.md#2.5 State machines and business rules`).
- **BR-15** The MVP has exactly one interactive CAPTCHA type. The second type, random selection and "Try another way" switching are in the backlog (`file:799940_answer.md#answer 5`, `msg:799941`).
- **BR-16** The type is not chosen yet (OQ-22). The ML developers pick it to fit their dataset and align it with the frontend developer; "drag an object along a randomly generated route" and "select shapes matching a condition" were only examples, and the user flow does not depend on the choice (`msg:799942`, `msg:799943`, `msg:799944`).
- **BR-17** Pass/fail is deterministic: task correctness and completion time. Speed, pauses, corrections and trajectory are features for ML and the Risk Engine, not pass conditions. The direction and values of the time limit are Open (OQ-23) (`file:799940_answer.md#answer 6`).
- **BR-18** Final assessment after the task: `human` passes, `suspicious` gets another attempt, `bot` gets the session temporarily blocked. How many attempts ("one more" or an admin-set maximum) is Open (OQ-23) (`msg:799646`).
- **BR-19** Blocks are temporary. Their duration, and whether they apply to the session or also to the client IP, are Open (OQ-21) (`msg:799646`, `file:818553_USER_FLOWS.md#UF-8 Expiry and returning visitor`).

### Tokens and gate

- **BR-20** All site traffic passes through Nginx, but only configured protected routes (e.g. login, registration, form submission) are checked; other requests are forwarded unchanged; no separate host is used (`file:799940_answer.md#answer 9`).
- **BR-21** On a protected route the browser sends the session cookie, Nginx asks the backend, and the backend returns the session status from PostgreSQL: `verified` forwards to the origin, `challenge_required` shows the challenge, `blocked` blocks. In the repo this is Nginx `auth_request` to `GET /v1/gate/check` (Repo); response codes and challenge UX are Open (OQ-12) (`msg:799646`, `file:799857_captcha_service_presentation.txt#Архітектура MVP`).
- **BR-22** Nginx runs no ML and holds no business logic; it forwards only allowed requests to the origin (`file:798550_captcha_service_plan.md#Додатково: Nginx proxy`, `file:799857_captcha_service_presentation.txt#Архітектура MVP`).
- **BR-23** The customer must close direct access to the origin so that it accepts traffic only from the proxy; the service cannot enforce this and must document it (`file:799857_captcha_service_presentation.txt#Підключення сайту адміністратором`, `file:818553_USER_FLOWS.md#UF-4 Protected-route gate (proxy)`).
- **BR-24** A `new` session, or a request without a cookie, on a protected route is treated as not verified and challenged (Proposed, DA-3; OQ-9) (`file:818551_DOMAIN_MODEL.md#1.5 Ambiguities that materially affect the design`).
- **BR-25** Verification token (Proposed; whether the token path is in the MVP is Open, OQ-1; design OQ-14): a short-lived token issued on `allow` or `human`, verified by the customer's server with the secret API key; token reuse is detected by a rule (`file:798550_captcha_service_plan.md#Додатково: Nginx proxy`, `msg:799646`).

| Session at a protected route | Gate answer                         | Basis                                                                                      |
| ---------------------------- | ----------------------------------- | ------------------------------------------------------------------------------------------ |
| `verified`, not expired      | Allow; Nginx forwards to the origin | Decided                                                                                    |
| `challenge_required`         | Challenge                           | Decided; HTTP code and UX Open (OQ-12)                                                     |
| `blocked`                    | Block                               | Decided; HTTP code and page Open (OQ-12)                                                   |
| `new`, or no cookie          | Not verified: challenge             | Proposed (DA-3, OQ-9)                                                                      |
| Gate or API unreachable      | Undefined                           | Open (OQ-11); the repo's sample Nginx config returns 500 for any answer except 2xx/401/403 |

### Site configuration and sensitivity

- **BR-26** Each site has a domain, allowed request origins, an origin backend address and a public site key used by the widget. A secret API key exists only for the token path (OQ-1) (`msg:799646`, `file:799857_captcha_service_presentation.txt#Підключення сайту адміністратором`).
- **BR-27** Sensitivity is one value per site from 0 to 100; the higher it is, the fewer suspicious signs the system needs to show a CAPTCHA or restrict requests. It shifts the `allow`/`challenge`/`block` thresholds; the mapping and the default value are Open (OQ-17) (`msg:799646`, `file:799940_answer.md#answer 2`, `photo:808975`).
- **BR-28** Administrators change only the sensitivity, never individual rules. Extra per-site parameters (maximum attempts, block duration, request limit) are Proposed and conflict with the "one sensitivity setting" scope (OQ-25); per-site CAPTCHA types and switching are post-MVP (`photo:808996`, `msg:799646`, `file:799940_answer.md#answer 5`).
- **BR-29** Project roles: an ADMIN has full control of the project; a DEVELOPER can configure parameters such as sensitivity but cannot delete the project or add developers. Key rights, multiple admins and ownership are Open (OQ-27) (`msg:816165`, `msg:816162`).

### Statistics

- **BR-30** Administrators see per-site statistics on traffic, CAPTCHA outcomes, risk scores and blocked requests, and outcomes are explained through statistics and risk levels; the product measures allow, challenge, block and false-positive rates. Metrics, time ranges and "risk levels" are Open (OQ-28) (`msg:799646`, `photo:808975`).
- **BR-31** The false-positive rate needs ground truth that live traffic does not have; until the team defines it, report decision rates, and label any approximation (e.g. the share of challenged sessions that later pass) as a proxy metric (Proposed) (`file:818553_USER_FLOWS.md#UF-9 Statistics`).

### Privacy and fingerprints

- **BR-32** Fingerprints are stored and compared only as hashes, with exact matching in the MVP and no similarity search (`msg:799960`). Repo rule: HMAC hashes only, and raw fingerprints are never logged, stored or returned (Repo). Composition and key management are Open (OQ-20).
- **BR-33** If the fingerprint changes significantly, the session is not automatically trusted and its risk score rises. With exact-match hashes "significant" is undefined (Proposed DA-4: any mismatch counts; OQ-20) (`msg:799958`, `file:818551_DOMAIN_MODEL.md#1.5 Ambiguities that materially affect the design`).
- **BR-34** A reputation record per (site, fingerprint hash) holds the average risk score and the numbers of successful verifications and blocks. The Risk Engine uses it as an extra signal when a new session is created, never as an automatic allow or block. The team lead stated this design without an explicit acknowledgement and noted that "nuances may change" (`msg:799960`, `msg:799961`).
- **BR-35** Collected behavioural data must be anonymised. What that means, retention, IP storage and consent were never discussed (OQ-32) (`file:798550_captcha_service_plan.md#Ідея та MVP`).

### ML role

- **BR-36** The ML model estimates the probability that a visitor is a bot from behavioural features, and the Risk Engine combines it with the rules. A score in [0, 1] was proposed; the repo leaves the score range and meaning as `TODO(team)` (OQ-16) (`msg:799646`, `file:798550_captcha_service_plan.md#6. ML-модель`, `msg:794492`).
- **BR-37** Feature extraction is a separate step before the model (`file:799857_captcha_service_presentation.txt#Шари FastAPI backend`). In the repo one implementation (`packages/features`) serves both the API and training, so there is no train/serve skew, and the API must not depend on pandas, scikit-learn or Jupyter (Repo).
- **BR-38** Start with rules and a simple baseline model; a neural model over cursor-movement sequences comes only after the team has its own dataset. The baseline algorithm (Random Forest or XGBoost in the plan) is Proposed; the repo's ML stack is scikit-learn (OQ-31) (`file:798550_captcha_service_plan.md#6. ML-модель`, `file:798550_captcha_service_plan.md#Стек`, `file:799857_captcha_service_presentation.txt#Після MVP`).
- **BR-39** Training data comes from the widget and a team-built bot behaviour generator, covering many bot types so the model does not overfit to one bot; public mouse-dynamics datasets are candidates whose fit was never assessed (OQ-30) (`file:798550_captcha_service_plan.md#Етапи`, `msg:794492`, `msg:794490`, `msg:798765`).
- **BR-40** Model quality is measured with precision, recall and false-positive rate (Proposed; a research topic, no targets) (`msg:815511`).

### Priorities and acceptance criteria

- No priorities (e.g. MoSCoW) were set. The proposed delivery order is: E0 foundation, with E6 data collection starting in parallel; then E1 tenant and site management and E2 sessions and signals; E3 rules-based Risk Engine; E4 verification (and token) with E6 model integration; E5 proxy enforcement; E7 statistics and test mode with E8 demo and validation (Proposed, `file:818552_EPIC_BREAKDOWN.md#1. Overview`).
- Jira stories get a Confluence spec: "As / I want / so that" plus two Given/When/Then acceptance criteria, one of them negative (`msg:815511`).
- Acceptance criteria proposed in `file:818552_EPIC_BREAKDOWN.md#2. Epics` (Proposed):
  - E1: the secret key is shown once; a developer can change sensitivity and policy but is refused when adding a member or deleting the project; sensitivity outside 0–100 is rejected; removing the only admin is rejected; a second site with an already registered domain is rejected.
  - E2: loading a page creates a `new` session and sets a cookie, and a reload reuses it; deleting the cookie or waiting past expiry gives a new `new` session; a cookie for site A is not accepted for site B; stored signals contain no direct personal identifiers and fingerprints only as hashes; the widget never exposes or sets the session ID.
  - E3: without ML, a scripted high-frequency client gets `challenge` or `block` and a normal low-rate browser gets `allow`; raising sensitivity moves the same input towards `challenge`/`block` (monotonic); a changed User-Agent or fingerprint raises the risk score; reputation alone never blocks or allows; each decision is stored with the sensitivity and rule evidence.
  - E4: `allow` gives a token with no visible UI; a correct, in-time answer can give a token and a wrong or too slow one is a failed attempt; after the maximum failed attempts the session is `blocked` for the configured duration; a token is accepted exactly once, with the correct secret key and only for its site.
  - E5: a protected route with a `verified` cookie reaches the origin, otherwise it does not; a non-protected route always does; an expired `verified` session is not honoured.
  - E6: a documented dataset with human traces and several bot behaviours; reproducible baseline metrics; with the model disabled the E3 criteria still hold.
  - E7: dashboard counts match stored decisions; one site's statistics never include another site's data.
  - E8: a human reaches a protected action and a scripted client without a valid session does not; the demo can be repeated from written instructions.

## Principles, values and team conventions

- **System-first.** Useful protection from rules before the model is accurate; ML adds criteria (`photo:808975`, `msg:798781`).
- **Challenge only when needed.** Keep the path simple for legitimate users (`photo:808975`).
- **MVP first; cut scope rather than overrun.** One CAPTCHA type, one monolith, PostgreSQL only, Redis and the sequence model deferred (`file:799940_answer.md#answer 4`, `file:799940_answer.md#answer 5`); if estimates do not fit, simplify or drop tasks (`msg:815672`); wireframes are low-fidelity, "it's not a design MVP" (`msg:800025`).
- **Reuse instead of building from scratch** ("nobody will build anything from scratch", said of the admin panel) (`msg:800029`).
- **Architecture describes intent.** The team lead's design says how things should work, and "in practice the nuances may change" (`msg:799961`).
- **Do not invent decisions.** Missing team decisions stay `TODO(team)` (Repo, `AGENTS.md`); several choices were explicitly delegated: the CAPTCHA type to the ML developers with the frontend developer (`msg:799942`), the widget framework to the frontend developer (`msg:800036`).
- **Research before building.** Study existing bots, datasets and CAPTCHAs; cover many bot types to avoid overfitting (`msg:794492`, `msg:794495`, `msg:815511`). Identify blockers early so members can work autonomously in parallel (`msg:815671`).
