## Product overview

Cursora is a bot-protection service for third-party websites. The name was adopted in the repository on 2026-10-21 (Repo) and not decided in the chat (`msg:808938`, `msg:818559`); the working title "CAPTCHA Service" still names the Figma file (`msg:808737`) and, spelled "CAPTHCA" (sic), the Jira project "CAPTHCA Service space" (`msg:816151`). An embedded JavaScript widget collects behavioural signals; a FastAPI backend with a rules-first Risk Engine, optionally helped by an ML score, decides `allow`, `challenge` or `block`; a challenged visitor gets an "I'm not a robot" checkbox and, if still suspicious, one interactive CAPTCHA. The main integration is token verification, as with reCAPTCHA: each registered site gets a public site key and a secret key; after the check the widget puts a short-lived verification token into the form, and the customer's backend verifies it with the Cursora API using the site's secret key; each token is accepted once. Many customer sites are supported from the start, and Cursora operates no proxy in front of them (team decision 2026-10-25 (after the export)). The Nginx gate in the repository is not an integration path: on 2026-10-25 the team answered that Nginx is only a reverse proxy without business logic, and whether the gate code is removed is Open (OQ-1). As designed: all of a site's traffic passes through it, it checks only the configured protected routes and forwards a request on them only when its session is `verified`, and other requests pass unchanged (`file:799940_answer.md#answer 9`). Site owners manage sites, sensitivity and statistics in an admin panel (`file:799857_captcha_service_presentation.txt#Короткий опис продукту`, `msg:799646`, `photo:808975`).

- **Problem:** "bots can imitate simple clicks, bypass frontend checks and attack the backend directly" (`file:799857_captcha_service_presentation.txt#Проблема та підхід`). Site owners need less spam, fewer brute-force attempts and automated requests on forms, registration, login and APIs, a backend that cannot be reached by bypassing frontend checks, and outcomes explained through statistics and risk levels ("risk levels" undefined, OQ-28); legitimate users need a simple path (`photo:808975`).
- **Vision (Product Vision Board, 2026-09-29):** "Give websites manageable bot protection that combines traffic rules, behavioural signals, and CAPTCHA only when needed." Differentiator: "System-first: useful protection before the model is accurate." (`photo:808975`)
- **Origin:** on 2026-09-03 a team member (later an ML developer) proposed a CAPTCHA service that tells bots from humans by cursor movement using ML, or alternatively a whole request proxy "something like Cloudflare"; the team lead extended it to an interactive CAPTCHA plus traffic and request analysis, with the CAPTCHA required only on suspicion (`msg:794483`, `msg:794493`, `msg:794496`).
- **Motivating scenario (informal, 2026-09-08):** protect the original articles of the team's previous course project (betterstack.dev, a site of articles comparing developer tools), proposed as the site to integrate the CAPTCHA into, from scraper ("plagiarist") bots (`msg:796940`, `msg:796949`, `msg:796951`, `msg:796952`, `msg:797392`); see OQ-3 and OQ-6.

### MVP scope

- In the MVP (Decided): a JS widget that collects behavioural signals; a checkbox plus one interactive CAPTCHA type (`file:799940_answer.md#answer 5`; the MVP slide's "two interactive CAPTCHAs" is superseded, CT-3); a FastAPI backend with the Risk Engine and an ML baseline; PostgreSQL for sessions and results; an admin panel with sensitivity and statistics (`file:799857_captcha_service_presentation.txt#Функціональність MVP`); token verification by the customer's backend with the site's secret key, for many customer sites from the start (team decision 2026-10-25 (after the export)). The same slide's "Nginx in front of the demo site" was reopened by that decision: whether the gate stays in the MVP is Open (OQ-1).
- Data for the model comes from the widget and a team-built bot behaviour generator (`file:798550_captcha_service_plan.md#Етапи`).
- Course-stage goal: "show the full path from the first request to the Risk Engine decision on a demonstration site" (`file:799857_captcha_service_presentation.txt#Функціональність MVP`).
- Business goals: deliver an integrated MVP that demonstrates site protection; validate the combination of rules, CAPTCHA and ML scoring; collect data for future model improvement; measure allow, challenge, block and false-positive rates (`photo:808975`).

## Business logic and domain rules

### End-to-end flow

Visitor (the 2026-09-14 user flow with the later clarifications and the 2026-10-25 integration decision applied, `msg:799646`):

1. The visitor opens a page of a site that embeds the widget (`<script src=".../widget.js" data-site-key="...">` in the repo).
2. The widget calls the session endpoint; the backend reuses the session from the cookie or creates a `new` one and sets the cookie (BR-1 to BR-3).
3. The widget passively collects behavioural signals; the backend gets request signals (IP, User-Agent, request rate) from the server or Nginx (BR-7).
4. Before a protected action the signals reach the backend, which applies the rules and the optional ML score and makes an initial decision: `allow` (no visible challenge), `challenge` (checkbox) or `block` (requests temporarily restricted) (BR-9, BR-10; timing Open, OQ-19).
5. A checkbox click sends the accumulated data; on success the session becomes `verified`; if the visitor still looks suspicious, one interactive task is shown (BR-13 to BR-15).
6. The task is checked deterministically (correctness, time) and the behaviour is scored: `human` passes, `suspicious` gets another attempt, `bot` is temporarily blocked (BR-17 to BR-19).
7. After a successful check the widget puts a short-lived verification token into the form; on the protected action the customer's backend verifies the token with the Cursora API using the site's secret key and proceeds only if it is valid; each token is accepted once (BR-25, BR-26). Only if the gate stays (OQ-1): on a protected route the browser sends the cookie to Nginx, Nginx asks the gate, and the session status decides: forward, challenge or block; other routes are forwarded without a check (BR-20 to BR-22).
8. After expiry `verified` no longer counts; the next visit gets a fresh `new` session, and reputation is used only as a soft hint (BR-3, BR-4, BR-34).

### Sessions and signals

- **BR-1** The backend owns the verification session. On initialisation the widget calls the session endpoint and the browser sends the session cookie automatically; the backend reuses a valid session or creates a new one and sets the cookie. The widget never generates and preferably never reads `session_id` (`msg:799950`, `voice:799948`, `file:799940_answer.md#answer 1`).
- **BR-2** Session IDs are generated by the backend and kept unique by a database constraint; a new session always starts as `new` (`file:799940_answer.md#answer 1`, `file:799940_answer.md#answer 8`).
- **BR-3** A new session is created only if there is no cookie or the session is missing, expired or invalid; otherwise it is reused. A new session never inherits the old status (`msg:799958`, `msg:799960`).
- **BR-4** Sessions are short-lived (`expires_at` in PostgreSQL) and bound to exactly one site; after expiry `verified` no longer counts and the visitor is assessed again. Lifetime values are Open (OQ-7) (`file:799940_answer.md#answer 4`, `file:799940_answer.md#answer 7`, `msg:799646`).
- **BR-5** `session_id` only links the HTTP requests of one session: it is not a risk signal and not proof on its own. User-Agent and fingerprint are extra signals against reuse of the ID or its transfer to another client, such as an HTTP client with a hard-coded cookie (`msg:799951`, `file:799940_answer.md#answer 7`, `file:799932_user-flow-review.md#step 14`).
- **BR-6** Behavioural signals are stored in the database as JSONB, linked to the session; a valid session is the main key for linking events (signals reference the session; the fingerprint is an extra signal) (`msg:799958`, `file:798550_captcha_service_plan.md#7. Data layer: PostgreSQL`, `photo:808975`). Each verification result is stored in PostgreSQL with its risk score and final decision (`file:798550_captcha_service_plan.md#7. Data layer: PostgreSQL`, `file:798550_captcha_service_plan.md#4. Application layer`, `file:799857_captcha_service_presentation.txt#Шари FastAPI backend`, `photo:808975`); an immutable record with the sensitivity in force, the rule evidence and the model version is Proposed (FR-20).
- **BR-7** Signal set (Proposed; the final list and client-side vs hybrid collection are Open, OQ-15): from the widget, passively, cursor movements or touches, clicks and the pauses between them, time on page, browser and device parameters; from the server or Nginx, IP, User-Agent and request frequency (`msg:799646`, `msg:799959`).

### Risk evaluation and decisions

- **BR-8** System-first: protection must work without ML. Rules decide on their own; the ML score is an optional extra input that "provides additional criteria for our backend". A missing or untrained model must not stop decisions (mechanics Open, OQ-31) (`msg:798781`, `photo:798757`, `photo:808975`).
- **BR-9** The Risk Engine combines rule results and the optional ML result into an initial decision: `allow` (pass without a visible challenge), `challenge` (show the checkbox) or `block` (temporarily restrict requests) (`msg:799646`, `file:798550_captcha_service_plan.md#5. Risk Engine`).
- **BR-10** The initial assessment runs before any visible challenge; the checkbox appears only when the server decides a check is needed (`file:799940_answer.md#answer 3`). The 2026-09-14 flow sends the widget's behavioural signals and the request signals "before a protected action" (`msg:799646` step 3), and the server decides from the widget's data whether to show the checkbox (`msg:799946`). Whether the assessment may run earlier (on page load, from request data only) was raised in review (`msg:799945`, `voice:799947`) and is not settled (OQ-19).
- **BR-11** Rules are internal (request frequency, headers, IP, session state, etc.): site administrators neither see nor edit individual rules (`file:799940_answer.md#answer 2`, `photo:808996`).
- **BR-12** Candidate rule inputs (Proposed; rule set, weights and combination Open, OQ-16): request rate, IP, User-Agent, suspicious headers, session state, session reputation, token reuse, signs of automated traffic, a form filled in too fast (`file:798550_captcha_service_plan.md#5. Risk Engine`, `msg:799646`, `file:799940_answer.md#answer 2`).

### Challenges (CAPTCHA)

- **BR-13** Verification is graduated: invisible assessment, then the checkbox (part of the widget), then, if the visitor still looks suspicious, one interactive task, then a final Risk Engine assessment (`file:799857_captcha_service_presentation.txt#Поступова перевірка`, `file:799940_answer.md#answer 3`).
- **BR-14** The checkbox click sends the accumulated behavioural data; on success the session becomes `verified` with the completion time recorded. What the click itself decides (a second "post-checkbox" assessment, DA-9) is Proposed (OQ-19) (`file:799940_answer.md#answer 3`, `msg:799646`, `file:818551_DOMAIN_MODEL.md#2.5 State machines and business rules`).
- **BR-15** The MVP has exactly one interactive CAPTCHA type. The second type, random selection and "Try another way" switching are in the backlog (`file:799940_answer.md#answer 5`).
- **BR-16** The type is not chosen yet (OQ-22). The ML developers pick it to fit their dataset and align it with the frontend developer; "drag an object along a randomly generated route" and "select shapes matching a condition" were only examples, and the user flow does not depend on the choice (`msg:799942`, `msg:799943`, `msg:799944`).
- **BR-17** Pass/fail is deterministic: task correctness and completion time. Speed, pauses and corrections are behavioural features for ML and the Risk Engine, not pass conditions (`file:799940_answer.md#answer 6`). Answer 6 does not mention the trajectory, which flow step 12 listed separately (`msg:799646`); treating it only as a feature is the reading of the summary and the design pack (Proposed), and for a route task it may be part of correctness (OQ-22, OQ-23). The direction and values of the time limit are Open (OQ-23).
- **BR-18** Final assessment after the task: `human` passes, `suspicious` gets another attempt, `bot` gets the session temporarily blocked. How many attempts ("one more" or an admin-set maximum) is Open (OQ-23) (`msg:799646`).
- **BR-19** Blocks are temporary. Their duration, and whether they apply to the session or also to the client IP, are Open (OQ-21) (`msg:799646`, `file:818553_USER_FLOWS.md#UF-8 Expiry and returning visitor`).

### Tokens and gate

Token verification is the main integration (BR-25, BR-26; team decision 2026-10-25 (after the export)). The Nginx gate, decided for the MVP on 2026-09-14 and present in the repository, is not an integration path any more: on 2026-10-25 the team answered that Nginx is only a reverse proxy without business logic; whether the gate code is removed from the repository is Open (OQ-1). BR-20 to BR-24 and the gate table below apply only if it stays; within that condition their own status labels hold.

- **BR-20** Gate scope (optional gate, OQ-1): all site traffic passes through Nginx, but only configured protected routes (e.g. login, registration, form submission) are checked; other requests are forwarded unchanged; no separate host is used (`file:799940_answer.md#answer 9`).
- **BR-21** Gate check (optional gate, OQ-1): on a protected route the browser sends the session cookie, Nginx asks the backend, and the backend returns the session status from PostgreSQL: `verified` forwards to the origin, `challenge_required` shows the challenge, `blocked` blocks. In the repo this is Nginx `auth_request` to `GET /v1/gate/check` (Repo); response codes and challenge UX are Open (OQ-12) (`msg:799646`, `file:799857_captcha_service_presentation.txt#Архітектура MVP`).
- **BR-22** Nginx role (optional gate, OQ-1): Nginx runs no ML (`file:798550_captcha_service_plan.md#Додатково: Nginx proxy`) and forwards only allowed requests to the origin (`file:799857_captcha_service_presentation.txt#Архітектура MVP`); it asks FastAPI and acts on the returned status (`msg:799646` steps 15–16). "No business logic in Nginx" is a Repo rule (`AGENTS.md`).
- **BR-23** Origin access (optional gate, OQ-1): the customer must close direct access to the origin so that it accepts traffic only from the proxy (`file:799857_captcha_service_presentation.txt#Підключення сайту адміністратором`, `msg:799646` admin steps 8 and 10). As the design pack notes, the service cannot enforce this (`file:818553_USER_FLOWS.md#UF-4 Protected-route gate (proxy)`); documenting the customer-side steps is Proposed (`file:818552_EPIC_BREAKDOWN.md#E5 — Proxy Enforcement of Protected Routes`).
- **BR-24** Unverified sessions at the gate (optional gate, OQ-1): a `new` session, or a request without a cookie, on a protected route is treated as not verified and challenged (Proposed, DA-3; OQ-9) (`file:818551_DOMAIN_MODEL.md#1.5 Ambiguities that materially affect the design`; no-cookie case: `file:818553_USER_FLOWS.md#UF-4 Protected-route gate (proxy)`).
- **BR-25** Verification token, the main integration (Decided: team decision 2026-10-25 (after the export); design details Open, OQ-14): after a successful check, on `allow` or `human`, the widget puts a short-lived token into the form, and the customer's backend verifies it with the Cursora API using the site's secret API key; each token is accepted once (`file:798550_captcha_service_plan.md#1. Frontend: JS CAPTCHA-віджет`, `file:798550_captcha_service_plan.md#2. Backend: FastAPI`, `file:798550_captcha_service_plan.md#Додатково: Nginx proxy`, `msg:799646`). The plan also detects token reuse with a risk rule (Proposed, BR-12). The 2026-09-14 presentation and answer 9 described only the Nginx session-status path, with no token or secret key (`file:799857_captcha_service_presentation.txt#Шлях відвідувача`, `file:799857_captcha_service_presentation.txt#Підключення сайту адміністратором`, `file:799940_answer.md#answer 9`); the 2026-10-25 decision returned to the token path of the 2026-09-10 plan (CT-1).

If the gate stays (OQ-1), it answers as follows:

| ---------------------------- | ----------------------------------- | ------------------------------------------------------------------------------------------ |
| `verified`, not expired      | Allow; Nginx forwards to the origin | Decided                                                                                    |
| `challenge_required`         | Challenge                           | Decided; HTTP code and UX Open (OQ-12)                                                     |

### Site configuration and sensitivity

- **BR-26** Each site has a domain, allowed request origins and a public site key used by the widget (`msg:799646`, `file:799857_captcha_service_presentation.txt#Підключення сайту адміністратором`). Each site also has a secret API key with which the customer's backend verifies tokens (Decided: `msg:799646`, team decision 2026-10-25 (after the export)); the plan also has the site authenticate to the API with an API key (`file:798550_captcha_service_plan.md#3. API layer`). Many customer sites are supported from the start; in the data model they are simply sites with keys (team decision 2026-10-25 (after the export)). The 2026-09-14 flow also gives each site an origin backend address (`msg:799646` admin step 2), which served a Cursora-operated proxy that the 2026-10-25 decision rules out; whether it is still stored is Open (OQ-2).
- **BR-27** Sensitivity is one value per site from 0 to 100; the higher it is, the fewer suspicious signs the system needs to show a CAPTCHA or restrict requests. It shifts the `allow`/`challenge`/`block` thresholds; the mapping and the default value are Open (OQ-17) (`msg:799646`, `file:799940_answer.md#answer 2`, `photo:808975`).
- **BR-28** Administrators never see or edit individual rules; they change the overall sensitivity (`file:799940_answer.md#answer 2`, `photo:808996`). Extra per-site parameters (maximum attempts, block duration, request limit) are optional settings in the team lead's 2026-09-14 flow (`msg:799646`), but answer 2 and the User Story Map note say the administrator changes one sensitivity setting; whether they are editable in the MVP is Open (OQ-25, CT-9). Per-site CAPTCHA types and switching are post-MVP (`file:799940_answer.md#answer 5`).
- **BR-29** Project roles: an ADMIN has full control of the project; a DEVELOPER can configure parameters such as sensitivity but cannot delete the project or add developers. Key rights, multiple admins and ownership are Open (OQ-27) (`msg:816165`, `msg:816162`).

### Statistics

- **BR-30** Administrators see statistics on traffic, CAPTCHA, risk scores and blocked requests (`msg:799646`); a per-site dashboard is Proposed (summary A12, `file:818553_USER_FLOWS.md#UF-9 Statistics`). Outcomes are explained through statistics and risk levels, and the product measures allow, challenge, block and false-positive rates (`photo:808975`); stored results: BR-6. Metrics, time ranges and "risk levels" are Open (OQ-28).
- **BR-31** The false-positive rate needs ground truth, and live traffic has no labels (`file:818553_USER_FLOWS.md#UF-9 Statistics`, `file:818553_USER_FLOWS.md#UF-10 Training-data collection (team-internal)`). An approximation such as the share of challenged sessions that later pass must be labelled a proxy metric, not FPR; E7 acceptance uses decision rates only (`file:818552_EPIC_BREAKDOWN.md#E7 — Statistics, Test Mode and Observability`) (Proposed).

### Privacy and fingerprints

- **BR-32** Fingerprints are stored and compared only as hashes, with exact matching in the MVP and no similarity search (`msg:799960`). Repo rule: HMAC hashes only, and raw fingerprints are never logged, stored or returned (Repo, `AGENTS.md`). Composition and key management are Open (OQ-20).
- **BR-33** If the fingerprint changes significantly, the session is not automatically trusted and its risk score rises. With exact-match hashes "significant" is undefined (Proposed DA-4: any mismatch counts; OQ-20) (`msg:799958`, `file:818551_DOMAIN_MODEL.md#1.5 Ambiguities that materially affect the design`). Whether this downgrades an already `verified` session before expiry, and whether the gate, if it stays (OQ-1), re-checks it, is Open (OQ-10).
- **BR-34** A reputation record per (site, fingerprint hash) holds the average risk score and the numbers of successful verifications and blocks. The Risk Engine uses it as an extra signal when a new session is created, never as an automatic allow or block. The team lead stated this design without an explicit acknowledgement and noted that "nuances may change" (`msg:799960`, `msg:799961`).
- **BR-35** Collected behavioural data must be anonymised. What that means, retention, IP storage and consent were never discussed (OQ-32) (`file:798550_captcha_service_plan.md#Ідея та MVP`).

### ML role

- **BR-36** The ML model estimates the probability that a visitor is a bot from behavioural features, a score in [0, 1] (Decided: `file:798550_captcha_service_plan.md#6. ML-модель`, `msg:799646` step 5; first suggested in `msg:794492`), and the Risk Engine combines it with the rules; how they combine, and the range of the combined risk score, are Open (OQ-16). The repo's `ml_port.py` still marks score range and semantics `TODO(team)` (CT-22).
- **BR-37** Feature extraction is a separate step before the model (`file:799857_captcha_service_presentation.txt#Шари FastAPI backend`). In the repo one implementation (`packages/features`) serves both the API and training, so there is no train/serve skew, and the API must not depend on pandas, scikit-learn or Jupyter (Repo). Example model inputs in the plan (Proposed; final set Open, OQ-15): mean and maximum cursor speed, number of sharp direction changes, pauses between movements and clicks, form completion time, number of requests in a short interval (`file:798550_captcha_service_plan.md#6. ML-модель`).
- **BR-38** Start with rules and a simple baseline model; a neural model over cursor-movement sequences comes only after the team has its own dataset. The baseline algorithm (Random Forest or XGBoost in the plan) is Proposed; Random Forest fits the repo's scikit-learn stack, while XGBoost would be a new dependency (OQ-31) (`file:798550_captcha_service_plan.md#6. ML-модель`, `file:798550_captcha_service_plan.md#Стек`, `file:799857_captcha_service_presentation.txt#Після MVP`).
- **BR-39** Training data comes from the widget and a team-built bot behaviour generator (`file:798550_captcha_service_plan.md#Етапи`). Covering many bot types to avoid overfitting to one bot is Proposed (`msg:794492`, 2026-09-03; `file:818552_EPIC_BREAKDOWN.md#E6 — Behavioural ML (data, baseline model, integration)`). Public mouse-dynamics datasets are candidates whose fit was never assessed (OQ-30) (`msg:794490`, `msg:798765`).
- **BR-40** Model quality is measured with precision, recall and false-positive rate (Proposed; a research topic, no targets) (`msg:815511`).

### Priorities and acceptance criteria

- The team lead's stage order (Decided as the plan, 2026-09-10 and 2026-09-14): preparation → data collection → backend and baseline → integration → completion; details in [Process and cadence](#process-and-cadence) (`file:798550_captcha_service_plan.md#Етапи`, `file:799857_captcha_service_presentation.txt#Етапи реалізації`). No priorities (e.g. MoSCoW) were set, and the Jira Timeline dates are not available.
- The design pack refines this into a proposed delivery order: E0 foundation, with E6 data collection starting in parallel; then E1 tenant and site management and E2 sessions and signals; E3 rules-based Risk Engine; E4 verification (and token) with E6 model integration; E5 proxy enforcement (only if the gate stays, OQ-1); E7 statistics and test mode with E8 demo and validation (Proposed, `file:818552_EPIC_BREAKDOWN.md#1. Overview`).
- The Jira Sprint 1 stories got a Confluence spec: "As / I want / so that" plus two Given/When/Then acceptance criteria, one of them negative (`msg:815511`, `msg:815703`); whether later stories follow the same template is not stated.
- Acceptance criteria proposed in `file:818552_EPIC_BREAKDOWN.md#2. Epics` (Proposed):
  - E0: one documented command starts the stack locally and a health endpoint responds; a pull request runs build and tests; the module layout and dependency rule are checked or documented (its four-context layout differs from the repo's five modules, CT-17).
  - E1: the secret key is shown once; a developer can change sensitivity and policy but is refused when adding a member or deleting the project; sensitivity outside 0–100 is rejected; removing the only admin is rejected; a second site with an already registered domain is rejected.
  - E2: loading a page creates a `new` session and sets a cookie, and a reload reuses it; deleting the cookie or waiting past expiry gives a new `new` session; a cookie for site A is not accepted for site B; stored signals contain no direct personal identifiers and fingerprints only as hashes; the widget never exposes or sets the session ID.
  - E3: without ML, a scripted high-frequency client gets `challenge` or `block` and a normal low-rate browser gets `allow`; raising sensitivity moves the same input towards `challenge`/`block` (monotonic); a changed User-Agent or fingerprint raises the risk score; reputation alone never blocks or allows; each decision is stored with the sensitivity and rule evidence.
  - E4: `allow` gives a token with no visible UI; a correct, in-time answer can give a token and a wrong or too slow one is a failed attempt; after the maximum failed attempts the session is `blocked` for the configured duration; a token is accepted exactly once, with the correct secret key and only for its site.
  - E5 (only if the gate stays, OQ-1): a protected route with a `verified` cookie reaches the origin, otherwise it does not; a non-protected route always does; an expired `verified` session is not honoured.
  - E6: a documented dataset with human traces and several bot behaviours; reproducible baseline metrics; with the model disabled the E3 criteria still hold.
  - E7: dashboard counts match stored decisions; one site's statistics never include another site's data.
  - E8: a human reaches a protected action and a scripted client without a valid session does not; the demo can be repeated from written instructions.

## Principles, values and team conventions

- **System-first.** Useful protection from rules before the model is accurate; ML adds criteria (`photo:808975`, `msg:798781`).
- **Challenge only when needed.** Keep the path simple for legitimate users (`photo:808975`).
- **MVP first; cut scope rather than overrun.** One CAPTCHA type, one monolith, PostgreSQL only, Redis and the sequence model deferred (`file:799940_answer.md#answer 4`, `file:799940_answer.md#answer 5`, `file:798550_captcha_service_plan.md#2. Backend: FastAPI`, `file:798550_captcha_service_plan.md#6. ML-модель`, `file:799857_captcha_service_presentation.txt#Після MVP`); if estimates do not fit, simplify or drop tasks (`msg:815672`); wireframes are low-fidelity, "it's not a design MVP" (`msg:800025`).
- **Reuse instead of building from scratch** ("nobody will build anything from scratch", said of the admin panel) (`msg:800029`).
- **Architecture describes intent.** The team lead's design says how things should work, and "in practice the nuances may change" (`msg:799961`).
- **Do not invent decisions.** Missing team decisions stay `TODO(team)` (Repo, `AGENTS.md`, imported by `CLAUDE.md`); several choices were explicitly delegated: the CAPTCHA type to the ML developers with the frontend developer (`msg:799942`), the widget framework to the frontend developer (`msg:800036`).
- **Research before building.** Study existing bots, datasets and CAPTCHAs; cover many bot types to avoid overfitting (`msg:794492`, `msg:794495`, `msg:815511`). Identify blockers early so members can work autonomously in parallel (`msg:815671`).
- **How decisions are made.** The team lead drafts the artefacts (plan, user flow, presentation, User Story Map, Jira, repository) and invites review in the chat; the lead answers with decisions (`msg:798785`, `msg:799646`, `msg:799940`). Some decisions are taken in calls (the 2026-09-11 kickoff, the 2026-10-19 grooming) and are known only from later references (`msg:799942`); there are no minutes.
- **Communication.** Discuss in the Telegram group so nobody has to be pulled into a call (`msg:798785`); post long replies as attached files (`msg:799940`) and short artefacts such as the user flow as plain chat text, so they can be read on a phone (`msg:799646`); @-mention a person when something is needed from them (`msg:800018`, `msg:800019`); candid, even emotional, review comments are fine (`msg:799932`, `msg:799933`); post task updates and repo questions in the chat (`msg:820040`); one member asked to be phoned when absent (`msg:809084`).
- **Scheduling.** Many members have jobs besides their studies (`msg:815669`): tell people about tasks at the weekend, because weekdays are hard (`msg:814838`, `msg:814840`). Calls are set when convenient for everyone (`msg:817919`); the grooming was set after 20:00 at a member's request and started at 21:00 (`msg:817922`–`msg:817924`, `msg:818262`).
- **Flexible roles.** No rigid boundaries (`msg:796964`); members take on unfamiliar roles and learn on the job (`msg:797400`). Half-time splits were floated on 2026-09-08 and 2026-09-09 but replaced by one role per member (`msg:796982`, `msg:797394`; CT-25).
- **Credit and participation.** At the 2026-09-29 and 2026-10-13 reviews each member had a part to present (`msg:808873`, `msg:808874`, `msg:816204`). The team lead stitches the parts together (`msg:808802`), presented the 2026-09-15 concept alone (`msg:799937`), stands in for absent members (`msg:816209`) and credits their authorship (`msg:808839`, `msg:808910`).
- **Confidentiality.** The team chat is confidential and is not shared outside the team (`msg:808885`); this document therefore names roles, not people, contains no private links and quotes the chat only where needed as evidence.
- **Language.** The chat and the early documents are in Ukrainian; product artefacts from 2026-09-29 (Product Vision Board, User Story Map, design pack) are in English; code, comments, commits and docs are in English (Repo, `AGENTS.md`).
- **Docker-first local development**, stated in banter: containers over all-in-one stacks such as WAMP/XAMPP, overhead judged negligible (`msg:800048`, `msg:800061`, `photo:800067`).
